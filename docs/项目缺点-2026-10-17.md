# R3 ShieldCore 缺点评估

> 2026-10-17。基于工作区实际代码与 git 状态，不含推测。
> 同目录下另有一份 `CODE-REVIEW.md`（更早写的），其结论已过期，见第 6 节。

## 一句话

逻辑层的自觉程度明显高于同类个人项目，但**工程层的防线几乎是空的**：仓库状态落后代码三代、
CI 不编译、单测几乎为零、关键约束写在仓库外的"铁律"注释里。真正会出事的不是 hook 写错了，
而是**改错了没有任何东西会告诉你**。

## 1. 仓库状态与代码状态脱节（最急，且是可立即修的）

- 最后一次提交是 2026-10-11 的 v78。之后 v79 / v80 / v81 三代的工作**全部停留在工作区**。
- 规模：25 个已跟踪文件被改，`+4563 / -1970`；另有 4528 行新文件未纳入版本控制，包括 6 个新共享头
  （`cfg_ipc.h` / `cfg_launch.h` / `log_line.h` / `md_inline.h` / `text_conv.h`）、
  `r3shieldcore_cfgipc.cpp/.h`、3 个新探针、13 张新截图。
- 工作区里还删掉了 3 份探针报告与 4 张截图（`docs/` 下），删除本身也没提交。
- 后果：现在 clone 这个仓库拿到的是 v78，**没有配置工具、没有命名管道日志、没有 Markdown 题面**，
  而 README 与 CHANGELOG 已经在描述这些能力。读者会以为文档在吹牛。

## 2. 没有自动化构建与测试防线

- `.github/workflows/gates.yml` 开头自述：完整构建"刻意不放进 CI"。CI 实际只跑 6 个纯文本
  Python 闸门（编码、引号、通配符、环境变量名、payload 清单）+ 3 个负对照。**一行 C++ 都不编**。
- 没有 gtest / catch2。`R3ShieldCore/tests/` 里只有 1 个文件（`test_mode_parse.cpp`，88 行）。
  真正的单测是 38 个 `tools/*_ut.cpp`，各自挂在 42 个 `build_*.sh` 里单独编译。
- 主要验证手段是 66 个 `*probe*.cpp` + 屏幕截图 + 日志 grep。这类判据本身很脆：
  `check_dist_sync.sh:1340` 自己写着"闸门查了个空文件却恒 PASS"；历史提交里也有
  "guard 层单测因 MSVC C1001 中断、一次都没执行过"的记录。
- 后果：改一处 hook 逻辑，没有任何自动手段能回答"那 312 处记账有没有被我砸掉"。

## 3. 手工记账与复制粘贴样板

- `g_activeHooks` 的 `InterlockedIncrement/Decrement` 在 `R3ShieldCoreLib/*.cpp` 里共 **312 处**，
  配平完全靠人。任何一条异常路径漏掉 Decrement，卸载时 `WaitForHooksToDrain` 就永久超时。
  改成 RAII scope 是零成本、一次改完 312 处的动作，现在还没做。
- `PromptFallbackVerdict()` 在 **17 个 guard 文件**里各有一份逐字相同的实现。
- 超大单文件：`r3shieldcore_gui.cpp` 4559 行、`r3shieldcore_rules.cpp` 4492 行、
  `registry_guard.cpp` 3500 行、`shared/r3shieldcore/r3shieldcore_shared.h` 2389 行。
  自绘 GUI 还把命中测试（`HitTestHeaderAction` / `HitTestArkButton` / `HitTestArkRow`）
  全写成手算坐标，加一个按钮要同时改绘制与命中共两处。

## 4. 安全设计上的先天短板

作者在 README 里已经承认了大部分，这里只补充代码层面的证据：

- **用黑名单解决白名单问题**：`inject_policy.cpp:26` 的 `kNeverInject` 是约 20 条硬编码进程名，
  且 `BaseNameInList()` 只比对**镜像基名** —— 改个文件名就能让它重新注入。
  更麻烦的是这份名单**不含引擎自身，也不含 IDE / 编译器**，于是"全局注入会 hook 编辑器导致崩溃"
  只能靠一条纪律（本机禁跑引擎）来兜。这是把系统性问题交给人的注意力。
- **引擎没有单实例互斥体**（README 第 10 节自认）：跑两份引擎就是两套 hook 互相打架。
  配置工具 `r3shieldcore-cfg.exe` 反而有单实例互斥体 —— 该有的没有，不该紧的紧了。
- **版本号与实际能力脱节**：`build.sh:60` 写死 `PRODUCT_VERSION="65.0"`，而代码与 CHANGELOG 已到 v81。
  发布包里的文件版本信息会误导使用者判断"我这版有没有那个功能"。
- 硬编码路径：`file_guard.cpp:516` 直接写死 `L"C:\\Windows\\"` 等系统目录，换语言/换系统盘就失效。
- 能力边界（README 已诚实说明，不算隐瞒，但要计入风险）：直 syscall、手工映射 DLL、复制令牌
  都能绕过；`dskill.exe` 是留下的逃生门，同时也是现成的绕过示范。

## 5. 构建与发布链过重

- `build.sh` 567 行 shell 直接驱动 `cl.exe / link.exe`（MSBuild 被安全策略按名拦截，属被迫选择）。
- 验收脚本 `check_dist_sync.sh` 是**单个 1472 行 / 72KB 的 shell 文件**，靠它一个人守整条发布链。
- 发布链 4 段：`build.sh` → `deploy_dist.sh` → `check_dist_sync.sh` → `build_dist_zip.sh`，
  中间还有 `build_verify_dist.sh`、`harden_dist_acl.sh`、`fix_bat_encoding.sh` 等。
  记忆里已经出现过两次"死闸门"（写好但没人调用）和一次"随包 ini 漂成 `mode=ask` 导致发布阻断"。
- 42 个 `build_*.sh`，其中约 28 个只编一个探针。工具链细节（INCLUDE/LIB 必须写成 `D:/` 而不是 `/d/`、
  MSYS 吞 `/FLAG` 所以 `dumpbin` 要用 `-SYMBOLS`）散落在这些脚本和记忆文件里，新人无法从代码推出。
- 四个 vendored 依赖：MinHook（BSD-2）、wow64ext（**LGPL-3.0**）、WIL（MIT）、
  ReflectiveDLLInjection（BSD-3）。合规靠 `THIRD-PARTY-NOTICES.md` 手工维护，
  而它是后期才补的（此前 LICENSE 版权栏为空）。

## 6. 关键知识在仓库外

- 代码里有 **573 处** `铁律 NNN` 形式的引用（`app.cpp:293/370/453` 等），而定义它们的
  `MEMORY-5-ironrules.md`（265 条）在 `.dev-assist/` 下、被 `.gitignore` 排除，**不在仓库里**。
  外部读者看到"铁律 175：本机禁止运行引擎"只能猜。
- 这是本项目最大的可维护性隐患：真正要命的约束既没有编译期强制，也没有仓库内文档，
  只存在于注释编号里。作者本人跨会话都要靠记忆索引去查。
- 文档体量已经过载：README 40KB、CHANGELOG 119KB、CONTRIBUTING 17KB。CHANGELOG 到 119KB
  基本等于"没人会读"。
- `docs/CODE-REVIEW.md`（18.9KB）**已过期**：它写于 gui.cpp 1632 行、tools/ 310 个文件、
  ABI 还在 v26 的时候（现状是 4559 行 / 283 文件 / v81）。它给出的最高优先级结论
  ——"v26 降级修复只覆盖 2/17 个 guard"——**现在已修**（`IsOpen()` 前置探测已覆盖 21 个文件）。
  一份过期的审查报告比没有报告更危险：它会让人按错误的前提去改代码。建议直接标注日期或重写。

## 7. 已知边界（作者主动声明，不计为隐瞒）

README 开头"使用前必读"与第 10 节已经把不成熟、易绕过、误报多、勿作唯一防护都写清了。
纯 GDI 自绘无托盘图标、极端 DPI 可能有布局问题、引擎必须管理员否则大面积失效，也都列了。
这部分是加分项，不重复批评。
