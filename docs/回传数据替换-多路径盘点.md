# 回传数据替换 — Phase 0 多路径盘点

> 状态：**纯盘点，未改任何产品代码**（新增 1 个独立探针，见 §4）。
> 前置：《回传数据替换Hook-技术预研》（`docs/回传数据替换Hook-技术预研.md`）。
> 目的：回答预研 §8 的 Phase 0 —— **"哪些面能形成闭环"**。
> 判据只有一个：**替换一条获取路径后，其余路径会不会给出真实值（戳穿）**。

---

## 0. 结论速览

| 数据面 | 已挂路径 | 漏掉的路径 | 闭环性 | 结论 |
|---|---|---|---|---|
| **屏幕像素** | BitBlt / StretchBlt / GetDIBits / PrintWindow | `GetPixel`、Desktop Duplication、WinRT Capture、D3D 前缓冲 | **部分** | ★ **可做**（既有盲区不变） |
| **剪贴板** | OpenClipboard / GetClipboardData | OLE 拖放、`NtUserGetClipboardData`、延迟渲染 | **部分** | ★ **可做** |
| **摄像头/麦克风** | avicap32 / MF 系列 / waveIn / mci；★ **MF 取帧（v73）**；★ **DirectShow 取帧（v75 探针：可替换）** | VFW 帧路径（★ v75 探针：**借屏幕面间接可替换**，非"不可替换"）、WinRT `MediaCapture`（★ v75 探针：路由明确、挂点可挂）、内核 | 部分 | ✅ **帧替换 v73**（同步 + 异步回调）；DirectShow 可接（未接）、WinRT 挂点已定位（未接）、VFW 借屏幕面（未接） |
| **注册表值** | 22 个 `NtXxx` + ★ **3 个 KTM 事务变体（v75）** | hive 文件直读（★ v75 探针：**活 hive 系统独占，不可行**）、`NtQueryKey` 个别 Class | **较好** | ✅ **值 v71 + 枚举 v72 + 事务准入 v75**（hive 直读已淘汰） |
| **系统时间** | 无 | 十余条（含 `RDTSC`） | **无** | ✗ 淘汰 |
| **文件内容** | 只挂**写**类；`NtReadFile` **未挂** | 内存映射 / 裸盘 / 备份 API / VSS / USN | **极差** | ✗ **淘汰** |
| **进程·模块·句柄枚举** | `NtQueryInformationProcess`（仅判据用） | `NtQuerySystemInformation` / Toolhelp / 句柄表 / PDH… | **极差** | ✗ **淘汰** |
| **网络数据** | connect / sendto / DNS / bind…（**仅发送侧**） | `recv`/`WSARecv` **未挂** + TLS + 内核 AFD | **无** | ✗ 淘汰 |

**一句话**：**只有"快照式、单次获取"的面（屏幕 / 剪贴板）能形成可接受的闭环**；
凡是有"同一份信息的多种读法"的面（文件 / 枚举 / 时间），替换一条必然被另一条戳穿。

---

## 1. 盘点方法

对每个面问三个问题：

1. **这个信息有几条获取路径？**（API 级，逐条列，不靠印象）
2. **我们已挂了几条？**（源码核对 `*_guard.cpp` 的 `QueueHook` / `GetProcAddress` 清单）
3. **替换已挂的那条之后，漏掉的那条会不会给出真实值？**（= 闭环性）

**判据口径（★ 关键区分）**：不是所有"多路径"都构成戳穿，要分两类：

| 类型 | 含义 | 是否戳穿 | 例 |
|---|---|---|---|
| **同一份信息的多种读法** | 同一时刻、同一对象、不同 API | ★ **必然戳穿** | 文件内容：`NtReadFile` vs 内存映射 vs 裸盘 |
| **同一对象的多次独立获取** | 每次获取是新的快照 | 不构成"戳穿"，但**换成另一条路就拿到真的** | 屏幕：`BitBlt` 一次 vs `GetPixel` 一次 |

第二类看着像漏洞，其实是**既有盲区**：`ScreenGuard` 本来就看不到 Desktop Duplication，
现在也看不到 `GetPixel` —— 替换**没有引入新盲区**，只是没覆盖既有的。

## 2. 逐面盘点

### 2.1 屏幕像素 ★

| 获取路径 | 现状 | 说明 |
|---|---|---|
| `gdi32!BitBlt` / `StretchBlt` | ✅ 已挂（`screen_guard.cpp:501/503`） | 应用层主路径 |
| `gdi32!GetDIBits` | ✅ 已挂（`:507`） | "第三条截屏路径"，v11 补的 |
| `user32!PrintWindow` | ✅ 已挂（`:512`） | 抓他人窗口 |
| **`gdi32!GetPixel`** | ❌ **未挂** | **逐像素读屏幕**。慢，但 `tools/_screen_probe.cpp` 已实测可行 |
| Desktop Duplication（`IDXGIOutputDuplication`） | ❌ 未挂 | **既有已知盲区**（`ScreenGuard` 注释自认） |
| Windows.Graphics.Capture（WinRT） | ❌ 未挂 | 现代截屏首选，DWM 侧合成 |
| D3D `GetFrontBufferData` / DWM 缩略图 | ❌ 未挂 | 少见但可行 |

**闭环性：部分**。但注意 §1 的类型区分 —— 这些都是"独立获取"，不是"同一份信息的多种读法"。
⇒ **替换 BitBlt/GetDIBits 得到黑帧是有效的**；攻击者换 Desktop Duplication 仍能拿到真画面，
但那是**既有盲区**，与替换能力无关。

**结论：★ 可做**。理由：单次调用、格式固定、无流式状态、无"必须与另一条路一致"的强约束。

### 2.2 剪贴板 ★

| 获取路径 | 现状 |
|---|---|
| `user32!OpenClipboard` / `GetClipboardData` | ✅ 已挂（`clipboard_guard.cpp:341/343`）；**v70 起 `GetClipboardData` 支持替换** |
| `user32!CloseClipboard` | ✅ **v70 新挂** —— 不是为拦截，是为**回收替代物**（句柄契约的终点） |
| OLE 拖放（`IDataObject::GetData`） | ❌ 未挂 |
| `win32u!NtUserGetClipboardData` | ❌ 未挂 |
| 延迟渲染（`WM_RENDERFORMAT` / `WM_RENDERALLFORMATS`） | ❌ 未挂 |

**闭环性：部分**。`GetClipboardData` 返回的是 `HANDLE`（全局内存句柄），
替换需要**分配一块自己的 GMEM 并改返回句柄** —— 比改 out 指针多一层"句柄所有权"语义
（谁 `GlobalUnlock` / 何时 `GlobalFree`），是**这个面特有的坑**，必须在设计里正面处理。

**结论：★ 可做**，但复杂度略高于屏幕。

> **→ 2026-10-10（v70）：已落地。** 实现与验证见
> `docs/回传数据替换Hook-技术预研.md` 的「落地记录（v70）」。
> 本节预判的"句柄所有权"确实是**这个面最费脑子的地方**，最终答案是：
> ① 只在 `CloseClipboard`（**原函数成功**时）回收；② 槽用**进程级固定数组**
> 而不是 `thread_local`（调用方未必是持有剪贴板那个线程）；
> ③ `CloseClipboard` 没挂上 ⇒ **本次不启用替换**（互锁，宁可退回拒绝）。
> 另加了一条本节没预判到的规则：**造不出合法布局的格式一律回落 `Block`**
> （`CF_TEXT`/`CF_BITMAP`/`CF_OEMTEXT`/`CF_DIB`/`CF_UNICODETEXT`/`CF_DIBV5` 之外
> 都不换）—— 硬造一个长度不对的块会让调用方读越界，那是替换**新引入**的崩溃面。

>   ① 注册表 `HKLM\SOFTWARE\Microsoft\WindowsRuntime\ActivatableClassId\`

>   `MFCreateCaptureEngine`，且**实测可被 `MH_CreateHook` 挂上**。

>   挂点 = `MFCaptureEngine.dll!MFCreateCaptureEngine`（**运行时加载，不在静态导入表**
>   ⇒ 需等加载或主动 `LoadLibrary`）+ `IMFCaptureEngine` vtable。
>   ⚠️ **真机 WinRT 激活未做**（`InitializeAsync` 是异步 + 要相机权限）——
>   本轮给的是"静态证据链 + 挂点可挂性"，不是"真机替换成功"。

### 2.4 注册表值

| 获取路径 | 现状 |
|---|---|
| `NtOpenKey` / `NtQueryValueKey` / `NtEnumerateKey` / `NtEnumerateValueKey` / `NtQueryKey` | ✅ 已挂（`registry_guard.cpp`，共 22 个 `NtXxx`） |
| `RegQueryValueEx` 等 `RegXxx` | ✅ 间接覆盖（走 `NtQueryValueKey`） |
| **事务注册表**（`NtCreateKeyTransacted` / `NtOpenKeyTransacted` / `NtOpenKeyTransactedEx`） | ✅ **v75 已挂**（准入判据；见下） |
| **hive 文件直读**（`\System32\config\*` 当**文件**读） | ✗ **v75 探针：不可行**（活 hive 被系统**独占**）—— 与 §2.6 同族淘汰 |
| 32/64 位重定向（`Wow6432Node`） | 部分（`NtQueryKey` 的 `KeyWow64FlagsInformation` 已在用） |

**闭环性：较好** —— 注册表 API 面是全项目**覆盖最全**的，`RegXxx` 最终都落到 `NtXxx`。
但仍有三个必须正面处理的点：**值类型与 `cbData` 长度**、**枚举游标（索引语义）**、
**事务 API**。

**结论**：三期。先做**值替换**（`NtQueryValueKey`），再做**枚举隐藏**（`NtEnumerateValueKey`）。

>   `NtEnumerateKey` / `NtSetValueKey`（这些 API 只看句柄，不区分句柄是不是事务的）
>   ⇒ **v71 的值替换、v72 的枚举隐藏本来就在事务句柄上生效**。
> - 真正缺的只有**"打开 / 创建"这一步的准入判据**：原来 `NtOpenKey` 的 detour
>   **不经过**事务变体 ⇒ 用 `NtOpenKeyTransacted` 打开受保护键，
>   能绕过"写不进 / 读不到 / 看不见"里的**第一道门**。
> - ⇒ v75 补的就是 `NtCreateKeyTransacted` / `NtOpenKeyTransacted` /
>   `NtOpenKeyTransactedEx` 三个"打开 / 创建"的事务变体，判据与
>   `Op::CreateKey` / `Op::OpenKey` **完全同源**。
> - ★★ **故意不给独立开关**：事务打开与普通打开是**同一个决策**，
>   给它一个开关等于**人为开一个洞**（关掉就能绕过 v71/v72）⇒ 跟随主判据、无条件挂。
>   （正因为如此，`check_dist_sync.sh` 的 v75 段有一条**方向相反**的判据：
>   随包 ini 里**不得**出现 `spoof_reg_ktm` 键。）
> - 三个导出一律 `required=false`（老系统上可能没有，缺了只少一层覆盖，
>   不能让整个模块失败 —— 与 `NtOpenKeyEx` 同一个处理）。
> - 实证：`tools/spoof_reg_ktm_probe.cpp`（自包含、不注入）**42 通过 / 0 失败 / 0 跳过**，
>   输出见 `docs/注册表KTM事务-机制探针-2026-10-11.txt`。关键四条：
>   ① 三个导出**与对应非事务版是不同的函数**（syscall 号也不同：
>      `NtOpenKey`=18 / `NtOpenKeyTransacted`=300 / `NtOpenKeyTransactedEx`=301 /
>      `NtCreateKeyTransacted`=182 / `NtOpenKeyEx`=299）；
>   ② **缺口成立**：关掉事务 detour 时 `NtOpenKeyTransacted(KEY_SET_VALUE)`
>      **能拿到受保护键句柄**，且**非事务 detour 完全没有被顺带触发**
>      ⇒ 事务变体不是内部转发到 `NtOpenKey`；
>   ③ **修复生效**：三个导出一律 `STATUS_ACCESS_DENIED`，且负对照（不受保护的键）仍放行；
>   ④ **"缺的只是准入"成立**：事务键句柄上三个 API **全部走到同一个 detour**，
>      v71 值替换 / v72 枚举隐藏都生效，且与非事务句柄上结果**逐字节相同**。
> - ★ **生产 v72 不会在事务句柄上静默降级**：探针实测
>   `NtQueryKey(事务键句柄, KeyNameInformation)` **能拿到路径**（事务 91 字符 ==
>   非事务 91 字符）⇒ `ResolveKeyPath` 这条路照样通。
> - ★ 事务语义实测：**读己之写成立**；`RollbackTransaction` 后值 `0xC0000034`
>   （回滚干净）；对照事务 `CommitTransaction` 后值读得到。
> - ★★ **探针踩到的坑（值得单独记）**：`NtOpenKey` / `NtOpenKeyTransacted`
>   **不接受预定义伪句柄**（`HKEY_CURRENT_USER` / `HKEY_LOCAL_MACHINE` /
>   `HKEY_USERS`）作为 `RootDirectory` ⇒ 一律 `0xC0000008 STATUS_INVALID_HANDLE`。

>   换成了真句柄** —— 这掩盖了上面的坑。Nt* 这条路只能用
>   ① `RootDirectory = 真键句柄` + 相对名；② `RootDirectory = NULL` + **绝对 NT 路径**。
>   （生产 `registry_guard.cpp` **不构造** `ObjectAttributes`，所以不受影响。）
> - `AbiVersion` **不变（26）**：没加新位、没改布局 —— 事务准入跟随主判据。
>
> **hive 直读（✗ 淘汰）** —— 结论 = **不可行**，与 §2.6「文件内容」**同族**。
> - 问题定性：走**文件路径**（`\System32\config\*`），决定性问题只有一条 ——
>   **"活 hive（已被系统加载）能不能被打开"**。
> - 实测（`tools/hive_read_probe.cpp`，输出见

>   - ⇒ 系统对活 hive 持**独占**句柄 ⇒ 打开不了 ⇒ 映射 / `RegSaveKey` 都无从谈起。
> - ⇒ 与"文件内容"同一个理由淘汰：**同一份信息的多种读法**，替换一条必被另一条戳穿。

### 2.5 系统时间

**闭环性：无**。`RDTSC` 是 CPU 指令，**用户态无法拦**。

**结论：✗ 淘汰。**

## 4. 探针实测：多路径戳穿已被实证

`tools/spoof_retdata_probe.cpp`（构建 `build_spoof_probe.sh`）—— **自包含**：
一个进程内自己挂自己的 hook，**不注入、不经过引擎、不读屏幕、不写盘**。

**本机实测输出（9 passed / 0 failed）**：

```
--- 阶段 0：基线（未挂任何 hook）---
  GetDIBits 返回行数=4  像素[0]=0x00FF0000          ← 真实（红）
  GetPixel(src,0,0)=0x000000FF                      ← COLORREF 是 0x00BBGGRR，顺序相反

--- 阶段 1：只挂 gdi32!GetDIBits ---
  GetDIBits 返回行数=4  像素[0]=0x00000000          ← 被替换成黑
  detour 命中=1 次  改写像素=32 个
  [PASS] 替换生效：调用者拿到伪造像素（全黑）
  [PASS] 返回码完好：返回行数 > 0（调用者看到"成功"，非 Block）
  GetPixel(src,0,0)=0x000000FF                      ← ★ 仍读到真实内容 = 戳穿

--- 阶段 2：只挂 gdi32!BitBlt ---
  BitBlt 返回=1 err=0
  目标 DC 像素[0]=0x00000000                        ← 对象状态被替换
  源   DC 像素[0]=0x00FF0000                        ← 源未受影响
```

**三条实测结论**（对应预研文档的三个论点）：

1. **机制可行**：detour 内「真调原函数 → 改写 out 缓冲区 → 返回原返回值」在本机跑通，
   调用者拿到伪造数据且**返回码完好** —— 这正是 Spoof 与 Block 的分水岭。
2. **多路径戳穿是真的**：只挂 `GetDIBits` 时，`GetPixel` **仍返回真实像素**。
   ⇒ 预研 §6.2「改一条 ≠ 覆盖这件事」**从推理变成了实测**。
3. **对象状态也能替换**：`BitBlt` 没有 out 指针，但目标 DC 的内容被替换、源未受影响。
   ⇒ 替换面**不限于 out 参数**，还包括"被写对象的最终状态"。

**附带发现**：`GetPixel` 读屏幕这条路径 `ScreenGuard` **当前未挂**（`tools/_screen_probe.cpp`
已实证它可用）。这是**既有盲区**，不是替换引入的 —— 但做屏幕替换时值得一并评估。
